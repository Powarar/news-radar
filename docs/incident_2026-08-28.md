# Production incident: VPS resource exhaustion on 2026-08-28

## Impact

The public site, API, SSH, and the VPN running on the same VPS became very slow.
Feed requests took 13-30+ seconds and SSH sometimes timed out before displaying
the server banner.

## Observed state

Initial read-only diagnostics showed:

```text
load average: 45.35, 39.28, 34.10
RAM:          1.9 GiB used of 1.9 GiB; 69 MiB available
swap:         511 MiB used of 511 MiB
disk:         60% used
```

The Celery container was unhealthy and reported 1422 PIDs. Backend child
processes repeatedly died and were respawned. Worker logs showed production was
still running the old Groq fallback: the removed `llama-3.1-8b-instant` returned
404, the remaining models returned repeated 429 responses, and each task slept
for up to 60 seconds per attempt. Individual AI tasks took 150-386 seconds.

## Reasoning

Disk capacity was healthy, while both RAM and swap were exhausted and the
system load was extreme. The VPN degraded at the same time as the web stack,
which ruled out a frontend-only or Cloudflare-only problem. Stopping optional
services immediately restored memory, confirming host resource exhaustion.

The first recovery priority was to stop new background work and restore the
API. Destructive database operations and a full VPS reboot were deliberately
avoided. The already-merged Groq fix was present in Git but not in the running
backend image, so only that image was rebuilt.

## Recovery commands used

Read-only host diagnostics:

```bash
hostname
date -Is
uptime
cat /proc/loadavg
free -h
df -h /
ps -eo pid,ppid,stat,comm,%cpu,%mem --sort=-%cpu | head -15
ps -eo pid,ppid,stat,comm,%cpu,%mem --sort=-%mem | head -15
docker stats --no-stream
docker ps
```

Temporarily stopped optional services:

```bash
for service in embedding-service flower grafana prometheus; do
  container_id=$(docker ps -q \
    --filter "label=com.docker.compose.service=$service" | head -1)
  if [ -n "$container_id" ]; then
    docker stop --timeout 20 "$container_id"
  fi
done
```

Stopped task production and cleared the backend process storm:

```bash
cd /home/newsradar/news-radar
docker-compose --env-file .env.prod -f docker-compose.prod.yml stop beat worker
docker-compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-deps --force-recreate backend
```

Rebuilt the backend with the merged Groq fallback fix and reloaded Nginx:

```bash
docker-compose --env-file .env.prod -f docker-compose.prod.yml build backend
docker-compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-deps --force-recreate backend nginx
```

Applied the resource-limited Compose configuration and restored background
processing:

```bash
docker-compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-deps --force-recreate backend embedding-service
docker-compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-deps --force-recreate worker
docker-compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-deps --force-recreate beat
```

The backend recreation changed its Docker IP after Nginx had already resolved
the upstream name. The frontend remained HTTP 200 while API paths returned 502.
Restarting Nginx refreshed the upstream address:

```bash
docker-compose --env-file .env.prod -f docker-compose.prod.yml restart nginx
```

## Permanent configuration changes

- Uvicorn workers reduced from 2 to 1.
- Celery concurrency reduced from 2 to 1.
- Celery child processes recycle after 100 tasks.
- Memory and PID limits added to backend, worker, and embedding service.
- Flower, Prometheus, and Grafana moved to the optional `observability` profile.
  They no longer start during the normal production deployment on a 2 GiB VPS.

Start observability deliberately only when the host has sufficient capacity:

```bash
docker-compose --profile observability --env-file .env.prod \
  -f docker-compose.prod.yml up -d flower prometheus grafana
```

## Recovery result

After stopping the background and observability services:

```text
load average: 1.98 (down from 45.35)
available RAM: 1.0 GiB (up from 69 MiB)
swap used: 219 MiB (down from 511 MiB)
```

External checks returned HTTP 200:

```text
root:        1.33 s
health:      1.75 s
20-item feed: 2.21 s
```

After all core services, embedding, worker, and beat were restored, the final
external checks remained healthy:

```text
health:       1.42 s, HTTP 200
20-item feed: 2.05 s, HTTP 200
load average: approximately 1.0
available RAM while idle: approximately 450 MiB
```

## Follow-up

Groq no longer receives requests for the removed Llama model, and failed model
chains complete in seconds instead of several minutes. Groq still intermittently
returns `json_validate_failed` and HTTP 429 for the replacement models. The
keyword fallback keeps ingestion operational, but structured-output quality and
rate-limit handling should be investigated separately.

## Rollback

Revert the resource-hardening commit and deploy the previous compose file. On a
2 GiB VPS, do not re-enable all observability services together unless resource
usage is monitored from the provider console.
